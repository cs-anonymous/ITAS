# 1 概述

## 1.1 目的

本文档为ITAS的测试文档。参考《构建之法-现代软件过程 第三版》中的描述，测试工作中需要撰写的测试文档主要包括测试计划（Test Plan）、测试设计说明书（TDS）、测试用例（Test Case）、测试报告（Test Report）。

根据本组理解，本文档中应尽可能覆盖以上四种文档的内容，因此本文档的目的在于：

- 测试计划策略：制定全面的测试计划和执行策略，适应可能的需求变更
- 测试设计说明：设计详尽的测试方案，包括产品介绍、测试目标、测试环境和测试方法，高效设计测试用例
- 测试用例执行：开发详细的测试用例，自动测试和手动测试结合，确保接口和功能的正确实现
- 测试评估报告：定义清晰的通过标准，深入分析测试结果，编制综合的测试报告

## 1.2 测试范围

本文档测试ITAS系统对应的《软件需求说明书v3.0》对应的所有功能性需求和非功能性需求的实现情况。其中功能性测试部分包括**白盒-接口测试**，**黑盒-Web端测试**；非功能性测试部分包括基本**响应速度测试**、**系统负载测试**、**压力测试**、**易用性测试**等。

详细的功能测试重点将在3.1节给出，非功能测试重点将在4.1节给出。

# 2 测试方法和计划

## 2.1 测试方案

整体测试方案：按照测试计划严格控制测试过程，与产品人员讨论需求，编写测试用例，与开发沟通测试中发现的问题，编写测试报告

测试类型：本说明文档进行所有的功能测试与非功能性测试

回归测试方案：对上一版本已解决问题和基础功能进行回归验证，以此保证原有功能正常

本次测试过程中，可能出现的风险如下：

1. 需求变更导致开发周期延迟从而导致的测试日期延后
2. 需求不明确导致的开发周期延迟从而导致测试日期延后

## 2.2 测试方法

白盒—接口测试
- 接口测试：验证后端服务的逻辑和功能，检查数据的输入、处理和输出是否符合预期。
- 测试用例设计：正常情况、边界条件、异常情况
- 自动化测试：自动化脚本测试
- 代码审查：可能的代码漏洞或安全漏洞

黑盒—Web端测试
- Web测试：模拟用户操作，验证前端页面功能与用户交互
- 功能测试：验证Web应用的所有功能点是否按照需求正常工作
- 用户体验测试：评估应用的易用性、交互设计、导航流程等
- 异常测试：拟用户的错误操作，验证系统对异常输入的处理能力
- 性能测试：评估系统在高负载下的表现，包括响应时间和系统稳定性
- 安全性测试：对Web应用的安全性进行测试，如防止SQL注入等

## 2.5 测试指标

### 2.5.1 测试用例优先级划分

测试用例的优先级根据产品功能的重要性和影响范围进行划分。在冒烟测试应筛选优先级最高的P0用例执行；在常规测试中，应优先执行等级高的P0、P1用例，在P0、P1用例全部通过的情况下，再执行P2、P3。

在编写测试用例时，应参照表3.1.1中的标准标注优先级。

        <th>优先级描述</th>
    </tr>
    <tr>
        <td>P0</td>
        <td>最重要的、最基础的功能。如果执行不通过，就会阻碍后面的测试工作。常作为冒烟测试的用例</td>
    </tr>
    <tr>
        <td>P1</td>
        <td>产品的核心功能。如果执行不通过，会影响产品的正常使用，会给客户带来非常不好的体验。常作为回归测试用例，每次新版本更新时，都需要复测的功能</td>
    </tr>
    <tr>
        <td>P2</td>
        <td>产品的一般功能。如果执行不通过，会影响某些小功能的使用，但大部分情况下不会阻碍客户的正常使用</td>

    </tr>
</table>

### 2.5.2 测试出现问题严重度划分

测试中出现的问题的优先级应根据问题对系统造成负面后果的程度进行划分，其中S1、S2、S3级别的问题为测试出现后需要全部解决的问题，S4、S5级别的问题为测试出现后需要与客户协商解决的问题，在某些条件下的留存不影响系统的正常交互。

### 2.5.3 测试通过标准

验收标准如下：

- S1级问题必须全部解决，功能机Test Case通过率必须为100%。

- S2、S3级问题必须全部解决，功能级Test Case通过率必须为100%。

- S4级问题应解决80%，否则认为相关缺陷较多，不予通过。

- S5级问题为建议修改，主要为增加体验，在允许的范围内也需尽量修改。


# 3 接口单元测试

本节主要描述使用Postman和Newman进行**集成测试**所用的**接口测试用例**。由于Web测试用例在大多数情况下拥有对应的接口测试用例，因此我们将用例表整合，方便厘清它们之间的对应关系。

在测试用例表中，我们共设计了11个字段，其中：

用例ID：每个用例的唯一标识符，最前面两位字符代表5.2节中的功能编号

优先级：测试用例的优先级，与表3.1.1所对应

接口（类）名称：接口测试时应访问的接口名称

用例名：每个用例的简单说明描述

请求方式：接口测试时应使用的请求方法，本系统中目前均为POST

前置条件：用例测试前需要确保满足的条件

请求参数：接口测试时需要传递的参数，""内为确定的实参，{{}}内为变量，需要提前调用其他接口获取，如使用登录接口获取SessionID

接口预期返回内容：符合Json格式，其中无法确定具体值的字段使用变量类型替代，如登录时为每个合法用户的每次登录生成一个随机字符串作为SessionID

## 6.2 风险分析及建议

由于本项目的测试周期较短，资源不足，测试中未涵盖的部分主要包括以下方面：

- 对于浏览器的兼容性测试不足，除在基于Chromium内核125.0版本和基于Firefox内核79.0版本的浏览器上进行测试外，尚未在其他内核版本和非上述内核的浏览器上进行测试。
- 对于安全性的测试不足，对于潜在可能出现的DDOS恶意攻击，F12篡改等部分测试不足，尚未考虑周全，当出现上述的恶意攻击情况时，系统可能崩溃。
- 对于生成功能潜在风险的测试不足，对于生成模型可能生成的非法内容，由于为小概率事件，在短暂测试周期中尚未遇到，由于概率模型的特性，也无法针对性进行风险消除。

## 6.3 测试结论

本项目根据业务需求，对客户的功能性需求和非功能性需求构建了**覆盖率100%的测试用例**。

截止目前为止，已在ST环境测试**15（接口测试）+64（Web测试）+16（非功能性测试）=95个**，完成度100%，

考虑测试人员反馈意见，**通过率为100%（95/95），缺陷关闭率为100%**。
