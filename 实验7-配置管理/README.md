## 1 配置管理说明

配置管理（Configuration Management，CM）是通过技术或行政手段对软件产品及其开发过程和生命周期进行控制、规范的一系列措施。

本小组主要使用Gitlab作为项目的配置管理工具，来记录软件产品的演化过程，同时完成实验文档的提交。本小组采用Gitlab对实验中的各阶段文档进行配置管理，在本地编制完成可提交的实验文档后，再统一上传至Gitlab。

本文章节结构如下：

第二章介绍了本小组如何使用Gitlab进行项目总体的配置管理。

第三章介绍了本小组的文档版本管理总结。

### 2.2 分支使用规范

在每次工作前，先使用git fetch/pull origin master获取远程库master分支的最新版本，修改完成后进行提交，最后将工作git push origin xxx推送至远程库的个人开发分支(xxx为本章中分支管理部分的个人分支名称)，并发起将本分支内容合并至master分支merge request。

完成该操作后由组内的审核人对本次Commit的修改进行审核，完成审核后，审核人批准本次merge request，master分支完成本次更新。


### 2.3 文件命名规范

#### 2.3.1 实验报告文件

- 命名规范：**[实验报告名称]_\[版本号\].md**
  - 实验报告名称：例如软件需求分析说明书、配置管理等
  - 主版本号更新规则：整合所有当前的次版本改动，并经过确认后，更新一个主版本，并将次版本号和修订号归零。
  - 修订号更新规则：只做了向下兼容的修正时才递增，即针对不正确的内容进行内部修改。
- 举例：**软件需求规格说明书\_v1.0.md**
- 例外：对于配置管理、软件工程实验追踪与分析、项目计划与进度控制分析、软件需求评审、软件测试评审，直接在目录下建立`README.md`，打开目录即可查看，避免层级冗余

#### 2.3.2 课堂汇报幻灯片

- 命名规范：**[小组编号]\-[周次]-[内容].pptx**
  - 只更新最新版本的ppt，避免前期改动带来繁琐的上传于更新，直接在微信群中更新
- 举例：**I组-第五次汇报-需求复评审.pptx**

#### 2.3.3 代码文件

- 命名规范：**[filename].ext**，文件名为英文单词或单词组合，若文件名为单词组合时，使用下划线相连。
- 举例：**save_geojson.py**

#### 2.3.4 会议记录

- 命名规范：**[日期].md**
- 举例：**0330.md**
